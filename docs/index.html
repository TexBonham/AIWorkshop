Part 1

Two ways "just ask" fails

A tiny tip splitter, one bug, two requests.

  • [3:00] Live demo on the instructor's account; screenshots in instructor/demo/ as fallback.
  • The example (tip.js) is deliberately not any of the labs. Target: done with both demos by ~7:00.

Failure 1: "fix the bug"

Youfix the bug
function splitBill(bill, tipPercent, people) {
  const tip = bill * tipPercent / 100;
  const share = bill / people + tip;
  return roundCents(share);
}
function roundCents(x) {
  let cents = Math.round(x * 100);
  if (cents % 1 !== 0) { cents = Math.ceil(cents); }
  return cents / 100;
}
AssistantFound it! roundCents is convoluted: the cents % 1 check can never be true. I've rewritten it as Math.round(x * 100) / 100. Fixed! Your tip splitter should work correctly now.

The rounding was ugly but correct. The real bug, $60, 20% tip, 3 people shows $32.00 each, expected $24.00, is untouched. It never heard the symptom.

  • [~3:30] Live demo on the instructor's account; screenshots in instructor/demo/ as fallback. Exact wording will differ live; the pattern is what matters.
  • Ask the room: what was the bug? (Tip isn't divided among people: 60/3 + 12 = 32.) Nobody told the assistant, so it fixed the ugliest code it saw and declared victory.
  • "Fixed!" is a claim, not a result. Hold that thought: habit 6.

Failure 2: "add X"

YouAdd an option to round each share up to the next dollar. (tip.js pasted)
AssistantDone! I added a roundUp option. While I was in there I also:
  • renamed splitBill to calculateShare for clarity
  • converted everything to arrow functions
  • formatted the result with a currency symbol

One request, four changes to review. The page still calls splitBill(), so now nothing works, and the display shows $$24.00.

  • [~5:30] Live demo on the instructor's account; screenshots in instructor/demo/ as fallback.
  • Point: the assistant is eager. Unasked "improvements" are where new bugs come from, and they make the real change hard to find.
  • Both failures are preventable with what you say, not with a better model. That's the next 7 minutes.

Start every chat with a short project brief: what the code is, what "done" means, what not to touch.

In a Project

No Projects?

Paste the brief as the first lines of message 1.

Skeleton #0 · it also bans refactors and "fixed!" claims for the whole chat.

  • [~7:00] Target: ~40 s per habit slide. You'll practise all of them in the labs.

Habits 2 and 3

Describe what you saw, then prove it

2 Symptom, not diagnosis

Say what you did, what you saw, what you expected. Don't guess the cause for it; a wrong guess sends it to the wrong place.

3 Reproduce, paste the real output

The exact wrong number. The red test lines, copied. Text, not screenshots.

What I saw:      $60, 20% tip, 3 people → $32.00 each
What I expected: $24.00 each ((60 + 12) / 3)

Skeletons #1 report a bug · #4 report back after testing

  • [~7:40] With these two lines, Failure 1 doesn't happen: it looks at the share math, not the rounding.
  • "I think the rounding is wrong" is a diagnosis. If you're wrong, it agrees with you anyway.
Habit 4

4 Plan before code, with assumptions

"List your assumptions and a plan. Don't write code yet."

  1. It lists assumptions and a numbered plan
  2. You correct the wrong assumptions
  3. You approve specific steps
  4. Then it writes code

A wrong assumption costs one line to fix in a plan, and a whole rewrite after the code.

Skeletons #2 assumptions + plan · #3 approve and correct

  • [~8:40] This is the habit that matters most for Labs 2 and 3. It feels slower; it is cheaper.
  • Reading the assumptions list is where you find out it misunderstood you, before you pay for code.
Habits 5 and 6

Steps you can check

5 One intention per request

Size the step to what you can still check: a line in a small file, a tested feature in a big one. Forbid changes you didn't ask for. "Show me only the changed lines."

6 Verify before you believe

It may run its own tests, and say so. Ask what it ran, and read what it says it did not test. Your checklist, in your browser, decides.

Skeletons #3 approve steps 1–3 only · #4 report back · #8 fix only these

  • [~9:40] Every lab has a tests page or a checklist. Its verdict beats the assistant's.
  • Free Claude has a code sandbox and uses it unprompted: in the dry run it ran the Lab 2 examples itself and drove a headless browser against its Lab 3 build. Useful, but its tests check its reading of the spec. Yours check yours. Skeleton #0 now asks it to say what it ran and what it did not test.
  • Scale: today a step is a line and you check after every edit, because the files are tiny. On a real project a step is a feature behind a test, and the check is one full run at the end of a stage. The size changes; "one intention" and "something other than the assistant decides" never do.
  • If it says "fixed" and the test is red, don't argue in prose: paste the red lines (#4).
Habit 7

7 Read the diff, own the decision

  • You are the reviewer. If you can't say which line changed and why, you're not done.
  • When a choice matters, make it argue against itself:
Give me the strongest case against this approach, and one
alternative. Then tell me which you'd pick and why. No code.

Skeleton #6 argue against it

  • [~10:40] Assistants agree with you by default. Asking for the case against is how you get the other side.
  • Lab 2 is where this pays off: the obvious fix is not the right one.
Habits 8 and 9

Keep chats short, spend on purpose

8 Fresh chat when context rots

Long chats drift and cost more per message. New lab = new chat. Your Project brief comes with you.

9 Budget your messages

Each lab has a spend plan. LABS.md says "Message 2 of 3" on every step that sends one.

Plan → approve → one change → test → report back.

  • [~11:40] Recap the loop in one line, then go.
  • Questions? Take one or two, max. Lab 1 starts at 14:00.

From a complaint to a spec

A complaint

"The search is broken." Real, but it doesn't say what right looks like.

A requirement

Examples with expected results: "I type X, I see A and B, I don't see C."

  • Examples are the spec. Write them before you open the chat
  • Ask for its assumptions: the gaps your examples don't cover #5 #2
  • Make it argue against the obvious fix #6
  • [~28:00] Bridge to Lab 2. Nothing is broken in Lab 2: every test passes. The code does what it was written to do, not what people expect.
  • You decide what "correct" is. The assistant can't, because only the owner knows.

From a brief to a build

Brief → spec → acceptance checks → one build → test locally → fix only what fails

Why one build

A whole page is a long reply. Each rebuild costs far more of your budget than a short answer. Settle the spec first, then build once.

Test it where it runs

The build arrives as an artifact with a Download button. Open the file in your browser and tick your list.

  • It will test its own build. Good. In Lab 2 its checks passed while one of your decisions was still open.

Skeletons #7 build from a brief · #3 approve · #8 fix round

  • [~47:00] An artifact is the panel where Claude shows a whole file. Show its Download button on the projector. In the dry run both builds arrived as downloadable artifacts.
  • Free accounts get a code sandbox: in the dry run it ran a headless browser against its own build unprompted. Its tests check its reading of the brief; theirs check theirs.
  • Fix rounds name the failing checks only. "Make it better" restarts the whole page.
